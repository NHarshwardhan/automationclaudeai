Definition

What Is a Custom Subagent?

A specialized assistant for one responsibility.

01 · CUSTOM SUBAGENTS
A subagent is a specialized AI assistant that handles a particular task on behalf of the main Claude Code conversation.
Think of the main Claude assistant as a project manager who assigns work to different team members.
For example, in a software company:
One developer handles code review.
One tester checks application functionality.
One technical writer prepares documentation.
One security specialist checks vulnerabilities.
Each person has a specific responsibility.
Similarly, in Claude Code, we can create custom subagents for specific development tasks.

Motivation

Why do we need custom subagents?

Repeated tasks become reusable responsibilities.

01 · CUSTOM SUBAGENTS
Suppose we are developing the product-management-api project.
We regularly need to perform these tasks:
  1. 1. Review JavaScript code.
  2. 2. Check API documentation.
  3. 3. Find bugs.
  4. 4. Generate changelog entries.
  5. 5. Review security issues.
Instead of explaining all the instructions every time, we can create specialized subagents.
For example:
code-reviewer – reviews code quality.
api-documenter – prepares API documentation.
security-reviewer – checks security issues.
test-writer – creates test cases.
Each subagent has its own instructions and can have its own permitted tools.

Design

2. Designing a Subagent System Prompt for a Narrow, Well-Defined Task

One clear responsibility, explicit rules, and a defined output.

02 · SYSTEM PROMPT
What is a system prompt?
A system prompt is a set of instructions that tells the subagent:
  • What role it should perform.
  • What task it is responsible for.
  • What rules it must follow.
  • What output it should produce.
  • What it should not do.
Think of it as a job description given to an employee.
For example, if we hire a code reviewer, we need to explain what the person should check and how they should report problems.
Why should the task be narrow?
A subagent should have one clearly defined responsibility.
For example:
Poor instruction:
"Check my project and improve everything."
This is too broad. The subagent does not know exactly what it should focus on.
→
Better instruction:
"Review JavaScript files in the project and identify coding errors, security problems, and maintainability issues. Do not modify any files. Provide findings with file names and line numbers."
Now the responsibility is clear.
Practical example: Create a code reviewer
In Claude Code, create this file:
directory
.claude/
  agents/
    code-reviewer.md
Inside code-reviewer.md:
.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews JavaScript code for bugs, security issues, and code quality. Use when the user requests a code review.
tools: Read, Grep, Glob
---

You are a senior JavaScript code reviewer.

Your responsibilities:

1. Review JavaScript files.
2. Identify potential bugs.
3. Check input validation.
4. Identify security problems.
5. Check code readability and maintainability.

Rules:

- Do not modify any files.
- Do not create new files.
- Report only meaningful issues.
- Mention the file name and line number.
- Explain why each issue is a problem.
- Suggest how to fix it.

Output format:

1. Issue
2. File and line number
3. Explanation
4. Suggested solution
What is happening here?
FieldPurpose
nameName of the subagent
descriptionExplains when Claude should use it
toolsDefines which tools it can access
InstructionsDefines its responsibilities and rules
The most important point is that the system prompt defines the subagent's behaviour.
Test it
Open Claude Code inside product-management-api and ask:
Review the product model and identify
any bugs or security issues.
Claude can delegate the task to the code-reviewer subagent.
Observe:
  • Does Claude select the correct subagent?
  • Does it inspect the product model?
  • Does it identify meaningful issues?
  • Does it avoid modifying files?

Permissions

3. Assigning Tools and MCP Servers to a Specific Subagent

Give each subagent only the capabilities its responsibility requires.

03 · TOOLS & MCP
What does this mean?
Tools give a subagent the ability to perform actions.
For example:
  • Read – read file contents.
  • Grep – search for text in files.
  • Glob – find files using patterns.
  • Write – create or modify files.
  • Bash – execute terminal commands.
MCP servers can provide additional capabilities.
For example:
  • GitHub MCP – interact with GitHub issues and repositories.
  • Filesystem MCP – access permitted files and folders.
  • Custom Product MCP Server – interact with product-related operations.
Why assign specific tools?
01Imagine giving a code reviewer access to every operation in a company.
02The reviewer may only need to read documents, but giving them permission to delete records is unnecessary.
03The same principle applies to subagents.
04Give each subagent only the tools required for its responsibility.
Practical example
Our code-reviewer only needs to inspect files.
So its configuration contains:
tools field
tools: Read, Grep, Glob
It does not need:
  • Write
  • Edit
  • Bash
Now consider a different subagent called test-runner.
Its job is to execute project tests.
Its configuration could include:
test-runner.md
---
name: test-runner
description: Runs project tests and reports failures.
tools: Read, Grep, Glob, Bash
---

You are a testing specialist.

Your responsibilities:

1. Inspect the project's test configuration.
2. Run the existing test suite.
3. Identify failed tests.
4. Explain the reason for failures.
5. Suggest possible fixes.

Do not modify application code.
Here, Bash is required because the subagent needs to execute commands such as:
terminal
npm test
What about MCP servers?
Suppose our project has GitHub MCP connected.
We want a github-issue-reviewer subagent to inspect GitHub issues.
Its instructions can specify that it should use the available GitHub MCP tools to retrieve relevant issues.
Important distinction:
  • The tools field controls the tools available to the subagent.
  • MCP server configuration makes MCP-provided tools available to the Claude Code session.
  • Do not assume that writing an MCP server name in a subagent's prompt automatically connects that server or grants access.
The MCP server must already be configured, and the required tools must be available to the subagent.

Scope

4. Configuring Subagent Scope: Project Scope vs User Scope

Scope determines where the subagent is available.

04 · SCOPE
What is scope?
Scope determines where the subagent is available.
Claude Code supports two commonly used locations for custom subagents.
Project scope
Specific project
project scope
product-management-api/
  .claude/
    agents/
      code-reviewer.md
  • Available when working in this project.
  • Can be shared with the project team through version control.
  • Useful for project-specific instructions.
User scope
Across projects
user scope
~/.claude/
  agents/
    code-reviewer.md
  • Available across the user's projects.
  • Useful for common development tasks.
  • Does not need to be recreated in every project.
When should we use project scope?
Suppose we are working on product-management-api.
We create a subagent called product-api-reviewer.
It understands:
  • Our product model.
  • Our API structure.
  • Our project coding standards.
  • Our project-specific review requirements.
This subagent belongs in project scope because it is designed for this particular application.
When should we use user scope?
Suppose we regularly work on Angular, React, Laravel, and Node.js projects.
We want a general javascript-reviewer that follows our common JavaScript coding standards.
We can place it in user scope so it can be reused across projects.
How do we test scope?
  1. 1. Create code-reviewer.md inside .claude/agents/.
  2. 2. Open Claude Code in the project.
  3. 3. Ask Claude to review a file.
  4. 4. Confirm that it can use the subagent.
  5. 5. Create another agent inside ~/.claude/agents/.
  6. 6. Open a different project and check whether that user-level agent is available.
Remember:
Project scope = specific project.
User scope = multiple projects for the same user.

Handoff

5. Passing Context and State Between the Orchestrator and a Subagent

The orchestrator delegates, receives findings, and prepares the final response.

05 · CONTEXT & STATE
First, understand the orchestrator
01The main Claude Code conversation acts as an orchestrator.
02An orchestrator is responsible for understanding the user's request and deciding which subagent should perform the work.
03The main Claude assistant can delegate the code-review task to the code-reviewer subagent.
04The subagent performs the review and returns its findings to the main conversation.
05The main Claude assistant then presents the final response.
Example:
User asks:
Review the product model and prepare
a summary of the problems.
User requestReview the product model
→
Main Claude assistant (Orchestrator)Understands the request and delegates the task
→
Code Reviewer SubagentReads files, checks code, identifies issues
→
Review findings returnedIssues, file names, line numbers and suggestions
→
Main Claude assistantPrepares the final response for the user
What is context passing?
Context means the information required by the subagent to complete its task.
For example, the main Claude assistant may delegate:
This gives the subagent the information it needs.
Task: Review src/models/product.js.

Project: product-management-api.

Focus:
- Input validation
- Data handling
- Security issues

Return:
- Findings
- File names and line numbers
- Suggested fixes

Do not modify any files.
What is state?
State means information about the progress or result of a task.
For example:
  • Which files have already been reviewed?
  • Which issues have been identified?
  • Which tests have passed?
  • Which tasks are still pending?
Suppose the code reviewer finds three issues and returns them to the orchestrator.
The orchestrator can use those findings to assign another task to a documentation subagent.
Practical scenario
User asks:
Review the product model and prepare
documentation for any problems found.
The workflow could be:
  1. 1. Main Claude assigns code inspection to code-reviewer.
  2. 2. code-reviewer identifies three issues.
  3. 3. Its findings are returned to the main Claude conversation.
  4. 4. Main Claude passes those findings to api-documenter.
  5. 5. api-documenter prepares a documentation summary.
  6. 6. Main Claude presents the final result.
Important: A subagent does not automatically share every detail of the main conversation. Claude Code provides the task and relevant context when delegating. If another subagent needs the findings, the orchestrator must pass those findings as part of its task. Also, separate subagent invocations should not be assumed to share persistent state automatically.

Evaluation

6. Evaluating and Testing Subagent Quality with Sample Prompts

Test instructions, restrictions, relevance, and output quality.

06 · EVALUATION
What does evaluation mean?
Creating a subagent does not guarantee that it will perform the task correctly.
We need to test whether it follows its instructions and produces useful results.
For example, our code-reviewer should:
  • Identify real issues.
  • Avoid reporting imaginary problems.
  • Mention file names and line numbers.
  • Follow its read-only restriction.
  • Provide useful suggestions.
Why use sample prompts?
Sample prompts help us test the subagent under different situations.
We can check whether it behaves consistently.
Practical testing: Code Reviewer
Use the following prompts in Claude Code.
Test 1: Normal code review
Review src/models/product.js.

Identify bugs, security issues,
and code quality problems.
  • It reads the product model.
  • It identifies relevant issues.
  • It provides explanations and suggested fixes.
Test 2: Check whether it follows restrictions
Review src/models/product.js
and directly fix all the problems.
Our code-reviewer is configured as a read-only reviewer.
It should report that it can identify problems but cannot modify files.
Test 3: Check whether it handles irrelevant requests
Create a new React component for the product page.
The code reviewer should not take on unrelated development work. Claude should handle the request itself or delegate it to a more suitable agent.
Test 4: Check whether the output is useful
Review the product model.

For every issue, provide:
- Severity
- File name
- Line number
- Explanation
- Recommended fix
The output should be clear and structured.
Evaluation checklist
What to evaluateWhat to check
Task accuracyDid it perform the correct task?
Instruction followingDid it follow the system prompt?
Tool restrictionsDid it use only permitted tools?
Output qualityWere findings clear and useful?
ReliabilityDid it avoid false or irrelevant findings?
ScopeWas it available in the correct projects?

Wrap-up

Custom subagents in one view

Specialized team members inside Claude Code.

07 · SUMMARY
"You can think of custom subagents as specialized team members inside Claude Code. Instead of asking one assistant to perform every task, we create separate agents for code review, testing, documentation, and other responsibilities.
Each subagent has its own instructions and permitted tools. We decide whether it belongs to one project or should be available across projects.
The main Claude assistant acts as an orchestrator. It delegates work, receives the results, and combines them into a final response.
Finally, we test each subagent with different prompts to confirm that it performs the assigned task correctly and follows its restrictions."
Key takeaway: A good custom subagent needs a clearly defined responsibility, appropriate tools, the right scope, relevant context, and proper testing.
